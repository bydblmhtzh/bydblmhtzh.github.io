Houdini Agent 制作思路逆向分析

2026-08-21 · 10 分钟阅读 · #Houdini#逆向#PySide6
目录

逆向对象：E:\tools\fast_work\Houdini Agent\（PyInstaller 打包，未加密，源码明文可见）
分析时间：2026-08-21
说明：本文为对朋友制作的软件做架构逆推与思路还原，非官方文档。

一、软件定位

一个「桥接 Houdini 的 AI 助手」。核心形态是：一个独立于 Houdini 运行的桌面 GUI（PySide6/Qt），通过把一段 Python 代码注入 Houdini 内部运行，用 MCP 协议操控 Houdini 节点，让 AI 能”看、改、建” Houdini 场景。

不是 Houdini 插件，也不是纯聊天机器人——是”外挂一个会操作 Houdini 的 agent”。

二、技术栈

层 选型
语言 Python 3.14（运行时）+ 兼容 3.9–3.13
GUI PySide6（Qt Widgets）+ QML（Qt Quick）双路线
打包 PyInstaller
关键依赖 tiktoken（token 计数）、numpy、lxml、cryptography/bcrypt（加密）、yaml、win32/_wmi（系统集成）

三、核心架构（五层）

1. 桥接层 bridge_payload/ —— 最关键的思路

软件本体（GUI）不寄生在 Houdini 里，而是把 bridge_payload 这个 Python 包注入 Houdini 的 Python 环境：

  • bridge/server.py + bridge/client.py —— Houdini 内部跑 server，GUI 跑 client，socket 通信
  • launcher/houdini_discovery.py —— 自动发现本机装的 Houdini 版本
  • houdini_package/python3.9libs ~ python3.13libs —— 多版本 Python 适配
  • shelf_tool.py + QUICK_SHELF_CODE.py —— 一键生成 Houdini Shelf 工具按钮

推断的思考：不同 Houdini 版本内置不同 Python（19.x→3.7/3.9，20.x→3.9/3.10/3.11，21.x→3.11+），所以制作者预置了 3.9~3.13 多套 libs，桥接代码跑在哪套 Houdini 里都能用。

2. MCP 协议层 utils/mcp/

用 Model Context Protocol 把 Houdini 操作封装成 AI 可调用的 tool：

  • hou_core.py —— hou 模块核心封装
  • tools/node_ops.py / param_ops.py / exec_ops.py / doc_ops.py / network_inspect.py —— 节点/参数/执行/文档/网络巡检五类操作

推断的思考：这是 2024–2025 MCP 热潮下的主流选择。制作者没有自己发明协议，而是套用 MCP 标准，让 AI 客户端（任何支持 MCP 的模型）都能直接接管 Houdini。

3. Agent 层 utils/

一整套会自我改进的 agent 基础设施：

  • plan_manager.py —— 计划（拆任务）
  • reflection.py —— 反思
  • reward_engine.py —— 奖励引擎
  • memory_store.py —— 记忆
  • growth_tracker.py —— 成长追踪
  • training_data_exporter.py —— 训练数据导出
  • token_optimizer.py + ultra_optimizer.py —— token 优化
  • tool_registry.py —— 统一工具注册中心
  • ai_client_providers.py + ai_client_streaming.py —— 多 AI 后端 + 流式
  • doc_rag.py + embedding.py —— RAG 文档检索
  • web_searcher.py —— 联网搜索

推断的思考：这是最有野心的部分。reward_engine + training_data_exporter 说明制作者想做”能收集好坏反馈、导出训练数据”的 agent（可能为后续微调模型做准备），不只是问答工具。

4. 扩展层 plugins/ + rules/ + config/

  • 插件系统：PLUGIN_INFO dict + register(ctx) 入口，事件钩子（on_before_request、on_after_tool 等 7 个）+ 装饰器（@hook / @tool / @ui_button）。ToolRegistry 显示 38+ 核心工具、9+ 技能。
  • 规则系统：.md/.txt 文件即规则，_ 前缀文件忽略。示例规则是「请使用中文回复」「节点命名用下划线」——本质是把提示词规则外置。
  • **技能 skills/**：预置 9 个 Houdini 分析脚本（cook 性能、法线、点属性、连通性、死节点、依赖追踪…）

推断的思考：制作者想把”可扩展性”做成产品卖点——用户不用改源码，写个 .py 插件或 .md 规则就能定制 agent 行为。这套设计很像 Claude 的 CLAUDE.md / 项目规则文件的思路。

5. UI 层 —— 双路线

  • ui/（Qt Widgets）：大量 mixin 模式拆分（context_mixin、history_mixin、memory_mixin、plan_mixin、streaming_mixin、system_prompt_mixin…）+ 富控件（plan_dag 计划图、thinking 思考块、tool_call、code_block markdown 渲染、syntax 高亮、theme 主题）
  • ui_qml/（QML）：Main.qml + 40+ 个 HAgent 组件（ChatView、PlanDag、PlanStream、ThinkingBlock、TodoBlock、TokenPopup、ProviderManager、SettingsWindow…）

推断的思考：先是用 Qt Widgets 快速搭出功能（mixin 把巨型主窗口拆成功能片），后来发现流式聊天 + 富交互用 QML 更顺，开始迁移。证据：qml_controller.pyc/qml_host.pyc 只出现在 cpython-314 缓存里（QML 是后加的新功能）。

四、关于 PyQt6 的考证（回应”他查了 PyQt6”）

制作者查的是 PyQt6 文档，实际用的是 PySide6，这是有意的、正确的选择：

qt_compat.py 写得很清楚——它同时兼容 PySide6 和 PySide2，注释原文：

“Houdini 20.5 及之前版本自带 PySide2，Houdini 21+ 自带 PySide6。”

关键洞察：桥接代码要跑在 Houdini 内部，而 Houdini 内嵌的是 PySide（不是 PyQt）。如果制作者用 PyQt6，会跟 Houdini 自带的 PySide 产生 Qt 运行时冲突（两个 Qt 绑定不能共存于同一进程）。所以必须用 PySide6。

而 PySide6 和 PyQt6 的 API 几乎一模一样（都是 Qt6 绑定），所以查 PyQt6 文档、用 PySide6 写代码完全可行，文档通用。这解释了”听说查了 PyQt6、实际是 PySide6”的现象。

五、制作者思考路径的逆推（时间线还原）

  1. 需求：让 AI 能操作 Houdini。
  2. 第一个决策：不写成 Houdini 内置插件，而是”外挂”——因为内置插件要跟随 Houdini 的 Python 版本、UI 框架，太受限；外挂 GUI 可以自由选最新 Python 3.14 + QML。
  3. 第二个决策：用桥接 + MCP，而不是在 Houdini 里直接跑 agent——把”操作 Houdini”抽象成标准工具，AI 后端可随意换。
  4. 第三个决策：选 PySide6 而非 PyQt6（Qt 运行时兼容性）。
  5. 野心膨胀：从”问答”升级成”会计划/反思/自我奖励/记忆/成长的 agent”，甚至加训练数据导出。
  6. 产品化：自动更新、遥测、国际化、主题系统、精选字体、插件市场、规则系统——都是”给别人用”的痕迹。

六、值得借鉴的工程细节

  1. qt_compat.py 兼容层：一处封装 PySide2/6 差异，全局统一导入，避免每个文件写 try/except。很干净。
  2. mixin 拆分主窗口：一个几百上千行的主窗口，拆成 xxx_mixin 多个文件，每个 mixin 管一块功能（历史、记忆、计划、流式…），可读性极好。
  3. 插件协议：PLUGIN_INFO + register(ctx) + 装饰器 + 事件钩子，是成熟的插件生态设计。
  4. 规则文件：把提示词规则外置成 .md，用户零代码定制。
  5. 多版本适配：python3.9libs~3.13libs 预置，解决 Houdini 各版本 Python 差异。
  6. 统一 ToolRegistry：核心工具 / 技能 / 插件工具 / 用户技能，四种来源统一注册到一处。

七、观察到的局限 / 可改进点（我的评价）

  1. API 密钥明文存配置：houdini_ai.ini 里明文存了密钥，建议改用系统凭据管理器（Windows Credential Manager / keyring）。（注：本文不记录任何密钥值。）
  2. 双 UI 并存成本高：Widgets 和 QML 两套 UI 并行维护，长期是负担，建议择一收敛。
  3. 多版本 libs 体积膨胀：3.9~3.13 全套打进包，8MB 主程序 + 大量 _internal 依赖，后续可考虑按需下载。
  4. PyInstaller 未加密：源码明文（.py + .pyc）可直接反编译，若有商业诉求建议加保护（但作为朋友作品，这也方便了学习和交流）。

本文基于只读逆向分析，未修改软件任何文件。
